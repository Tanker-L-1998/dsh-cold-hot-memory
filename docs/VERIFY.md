# 验证机制

## 为什么有这份文档

2026-11-11 的一次审计发现：有四项能力在讨论中"确认过"，也在 changelog 里写着"已完成"，但代码里根本不存在——版本兼容检测、写失败重试、原子写、schema 迁移。

根因不是疏忽某一项，而是**流程缺一环**：把"讨论过"当成了"做完了"。

这份文档定义那一环。

## 发版前必做两件事

```bash
node scripts/verify.mjs    # 静态核对：每条声称的能力是否真的在源码里
node test-store.mjs        # 行为测试：35 项
```

`verify.mjs` 会逐条打印 PASS/FAIL，任何一条 FAIL 就以非零退出码结束——**不允许发版**。

## 它检查什么

`scripts/verify.mjs` 里有一张 `CAPABILITIES` 表，每行是「能力名 + 一个必须出现在源码里的正则」。

加一个新能力时，必须同时加一行；否则下次验证不会覆盖它。

## 它查不出什么

静态检查只能证明"代码里有这个东西的痕迹"，证明不了：

- 逻辑对不对（靠 `test-store.mjs`）
- 在真实宿主里能否运行（靠重启后的人工验收）
- 边界条件是否覆盖（靠用例）

所以三个层次缺一不可：

| 层次 | 手段 | 能发现 |
|---|---|---|
| 有没有 | `verify.mjs` | 声称做了但没写 |
| 对不对 | `test-store.mjs` | 逻辑错误 |
| 能不能跑 | 重启后验收 | 集成问题 |

## 加新能力时的顺序

1. 写代码
2. 在 `test-store.mjs` 加用例（行为）
3. 在 `scripts/verify.mjs` 的 `CAPABILITIES` 加一行（存在）
4. 跑两个脚本
5. 更新 README 的"当前进度"
6. 提交

跳过第 3 步，就等于放弃这道检查。
