# dsh-cold-hot-memory

给 [DeepSeek Harness](https://deepseek.com) 的分层记忆插件 —— 让长会话记得住**做到哪、定了什么、还欠什么**。

> **状态：v1.0。** 27 项测试通过；已在 DeepSeek Harness 桌面版 0.2.1-rc.2 上完整验证（工具注册、清单注入、脱敏拦截、回活、单写者 inbox 均实测）。
> 仍是个人自用工具：没有 UI，检索是纯关键词。

---

## 为什么需要它

长会话的敌人不是"记不住"，是"记不下"。

上下文窗口是硬的，塞满了就必须压缩。而压缩是**有损**的：把早期对话换成一段摘要，原文就再也看不见了。

这个插件不试图阻止压缩，而是换一个前提：

> **完成的事大部分不会再被提起。所以过程可以丢，结论必须留。**

---

## 三层记忆

| 层 | 存什么 | 放在哪 | 寿命 |
|---|---|---|---|
| **状态** | 现在做什么、卡在哪 | `state.md` | 每轮覆盖，只保留最新 |
| **结论** | 定了什么、为什么、依据 | `decisions/` | 长期，不可改写 |
| **未完成** | 没做完的事 + 恢复卡 | `open/` | 30 天沉睡，90 天归档 |

一张"恢复卡"只有五行，够下次接着干就行：**目标、现状、阻塞、下一步、指针**。

### 记忆放在哪里

**跟着项目走**，不集中存放。项目路径取自会话的 `cwd`：

```
<项目根>/.dsh-memory/
├── project.json
├── shared/              结论 / 归档 / 引用 / 交付流水（项目级，所有对话共享）
└── conv/<会话>/          状态 / 卡片 / inbox（对话级，仅本对话可写）
```

这样项目换位置记忆跟着走，不同项目的结论也不会混在一起。

> **建议把 `.dsh-memory/` 加进项目的 `.gitignore`** —— 里面有内部讨论和决策，不该推到远端。

### 从旧版升级

1.1 之前，所有项目共用一个全局目录（`~/.dsh/memory`）。升级后第一次在某个项目里运行时，插件会自动：

1. 把旧目录整体复制到 `<项目>/.dsh-memory/`
2. 写一份 `LEGACY-IMPORT.md`，说明其中混着多个项目的结论、需要自行归类
3. 把旧目录改名为 `memory.migrated-<时间>` —— **改名不删除**，可随时回退

为什么不做精确拆分：会话级数据（状态、卡片、inbox）能从会话头里的项目路径判断归属；项目级的 `shared/` 没有这个字段，任何"智能拆分"都是猜测。宁可明说混在一起，也不假装分对了。

## 五条设计原则

### 1. 交付即完成，不等用户确认

大多数记忆系统都要人手动"标记完成"。现实是没人会这么干——于是"未完成"列表越堆越长，最后变成噪音。

这里改成：**产物落地就标为已交付**；有新要求时，用户一句话就重开。

> 挂着不关的成本是持续噪音，重开的成本是一句话。

### 2. 结论不可变，方案原地改

| 类型 | 修改方式 | 原因 |
|---|---|---|
| 结论 | 新建一条，旧的进 `archive/` | 结论记录的是"当时怎么判断的"，改写会毁掉证据 |
| 方案 | 原地改同一个文件 | 方案是活文档，最新版只该有一份，否则文件夹爆炸 |

原地改的留痕方式：文件内部一个 `## 变更记录` 小节，只追加。

### 3. 没人会说"不用管了"，所以用时间老化

`closed` 这个状态在现实中几乎不会发生——方案永远有优化空间。

所以不靠用户宣布结束，靠时间：

```
delivered ──30天──► dormant ──90天──► archived
     ▲                  │
     └──── 任何提及 ─────┘
```

任何一次提及都会让它立刻回到活跃，用户什么都不用做。

### 4. 敏感信息写入前拦截

中英文标签都认：`密码：`、`密钥`、`api_key=`、`token:`、`-----BEGIN PRIVATE KEY-----`。

命中即拒绝写入，除非显式放行。

### 5. 中文友好

- **分词**：双字滑窗（bigram），而不是把整段中文当一个词——后者会让中文检索几乎失效
- **排序**：BM25 + 层级权重 + 置信度 + 时间衰减
- **token 估算**：区分 CJK / ASCII / 其他，中文按 1 字 ≈ 1 token 算（`len/2` 会低估一半）

## 一条记忆的生命周期

```
        ┌──────────┐
        │ planning │  出方案
        └────┬─────┘
     批准方案 │
        ┌────▼─────┐
        │executing │  落实
        └────┬─────┘
     产物落地 │
        ┌────▼─────┐
        │delivered │  已交付，可随时重开
        └────┬─────┘
   30天没动静 │
        ┌────▼────┐
        │ dormant │  不再注入上下文
        └────┬────┘
   90天没动静 │
        ┌────▼─────┐
        │ archived │  移出主索引
        └──────────┘
```

## 注册的工具

| 工具 | 作用 |
|---|---|
| `memory_state` | 读 / 覆盖"现在在做什么"（保留上一版 `.bak`） |
| `memory_card` | 开卡片、推进阶段、列出卡片 |
| `memory_decision` | 记录结论 / 推翻旧结论（旧的自动归档） |
| `memory_recall` | 跨卡片、结论与引用的关键词检索 |
| `memory_ref` | 从其他项目复制一份只读快照（一次性 fork，不跟随源更新） |
| `memory_stats` | 各阶段计数、结论/引用数、注入清单大小，可触发老化 |

## 安装（已验证）

以本地 bundle 形式装入 DSH profile：

```json
// ~/.dsh/profiles/desktop/package.json
{
  "dependencies": {
    "dsh-cold-hot-memory": "link:E:/DeepSeekHarness/dsh-plugin-memory"
  },
  "dsh": {
    "profile": {
      "bundles": ["@deepseek-ai/dsh-base", "@deepseek-ai/dsh-web-app", "dsh-cold-hot-memory"]
    }
  }
}
```

然后在 profile 目录执行 `pnpm install`，重启 DSH。

**验证方式**：插件启动时会往 `.runtime/loaded.log` 写心跳，正常应看到五行：

```
module-imported → apply-start → imported-dsh-tools → imported-dsh-llm → tools-registered
```

## 写 DSH 插件的四个坑（亲测踩过）

1. **模块顶层不要 `import` 第三方包。** 一旦宿主里解析不到，整个模块在导入阶段就失败，而 DSH 对非必需插件只给一条不可见的警告——界面照常启动，你以为装好了，其实没加载。
   修法：顶层只 `import` 本包文件和 `node:` 内置模块，第三方包放到 `apply()` 里动态 `import()`，失败时写进心跳。

2. **link 安装的包必须自带 `node_modules`。** 宿主的模块解析不会替你补 peer 依赖。

3. **加载失败没有任何提示。** 除非自己写心跳文件，否则无法区分「没加载」和「加载了但坏了」。

4. **`package.json` 不能带 BOM。** 用 PowerShell 的 `Set-Content -Encoding UTF8` 改文件会写入 BOM（`EF BB BF`），加载器用 `JSON.parse` 解析时直接抛 `SyntaxError: Unexpected token '﻿'`，然后**静默跳过整个 bundle**。PowerShell 自己读得懂 BOM，所以肉眼看不出问题。
   修法：用编辑器保存为 UTF-8 without BOM，或 `[IO.File]::WriteAllText($path, $text, [Text.UTF8Encoding]::new($false))`。

## 设计取舍

**为什么做关键词检索，不做向量检索？**
零依赖、可解释、无额外成本，而且规模小的时候关键词足够准。代价是同义词和语义相似处理不了。等规模上来再换。

**为什么用文件，不用数据库？**
可读、可 diff、可备份、可手工修。代价是要自己处理并发写——目前还没做。

**为什么不干脆取消压缩？**
窗口是硬的，做不到"什么都不丢"。能做的是"丢内容、留指针"：一句话就能追回原文。

**为什么结论不直接改？**
因为三个月后真正想问的不是"现在怎么做"，而是"当初为什么没选另一条路"。改了就没有答案了。

## 已知限制

- 没有 UI
- 检索是纯关键词，无语义相似度
- 配置目前只读默认值（未导出 schemastery 的 `Config`，以免引入模块级第三方依赖）
- 老化只在调用 `memory_stats(sweep=true)` 或 `memory_recall` 时触发，没有后台定时器
- 引用是快照，源项目后续的更新不会同步过来（这是有意的：适合别人的方案不一定适合自己）
