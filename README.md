# dsh-cold-hot-memory

给 [DeepSeek Harness](https://deepseek.com) 的分层记忆插件 —— 让长会话记得住**做到哪、定了什么、还欠什么**。

> **状态：v0.2 实验版。** 引擎层 18 项自测通过；**已在 DeepSeek Harness 桌面版 0.2.1-rc.2 上装载验证通过** —— 5 个工具注册成功，记忆清单注入生效。
> 数据模型仍在重写中（见"当前进度"），请勿用于重要数据。

---

## 为什么需要它

长会话的敌人不是"记不住"，是"记不下"。

上下文窗口是硬的，塞满了就必须压缩。而压缩是**有损**的：把早期对话换成一段摘要，原文就再也看不见了。

这个插件不试图阻止压缩，而是换一个前提：

> **完成的事大部分不会再被提起。所以过程可以丢，结论必须留。**

---

## 三层记忆

| 层 | 存什么 | 放在哪 | 寿命 |
|---|---|---|---|
| **状态** | 现在做什么、卡在哪 | `state.md` | 每轮覆盖，只保留最新 |
| **结论** | 定了什么、为什么、依据 | `decisions/` | 长期，不可改写 |
| **未完成** | 没做完的事 + 恢复卡 | `open/` | 30 天沉睡，90 天归档 |

一张"恢复卡"只有五行，够下次接着干就行：**目标、现状、阻塞、下一步、指针**。

---

## 五条设计原则

### 1. 交付即完成，不等用户确认

大多数记忆系统都要人手动"标记完成"。现实是没人会这么干——于是"未完成"列表越堆越长，最后变成噪音。

这里改成：**产物落地就标为已交付**；有新要求时，用户一句话就重开。

> 挂着不关的成本是持续噪音，重开的成本是一句话。

### 2. 结论不可变，方案原地改

| 类型 | 修改方式 | 原因 |
|---|---|---|
| 结论 | 新建一条，旧的进 `archive/` | 结论记录的是"当时怎么判断的"，改写会毁掉证据 |
| 方案 | 原地改同一个文件 | 方案是活文档，最新版只该有一份，否则文件夹爆炸 |

原地改的留痕方式：文件内部一个 `## 变更记录` 小节，只追加。

### 3. 没人会说"不用管了"，所以用时间老化

`closed` 这个状态在现实中几乎不会发生——方案永远有优化空间。

所以不靠用户宣布结束，靠时间：

```
delivered ──30天──► dormant ──90天──► archived
     ▲                  │
     └──── 任何提及 ─────┘
```

任何一次提及都会让它立刻回到活跃，用户什么都不用做。

### 4. 敏感信息写入前拦截

中英文标签都认：`密码：`、`密钥`、`api_key=`、`token:`、`-----BEGIN PRIVATE KEY-----`。

命中即拒绝写入，除非显式放行。

### 5. 中文友好

- **分词**：双字滑窗（bigram），而不是把整段中文当一个词——后者会让中文检索几乎失效
- **排序**：BM25 + 层级权重 + 置信度 + 时间衰减
- **token 估算**：区分 CJK / ASCII / 其他，中文按 1 字 ≈ 1 token 算（`len/2` 会低估一半）

## 一条记忆的生命周期

```
        ┌──────────┐
        │ planning │  出方案
        └────┬─────┘
     批准方案 │
        ┌────▼─────┐
        │executing │  落实
        └────┬─────┘
     产物落地 │
        ┌────▼─────┐
        │delivered │  已交付，可随时重开
        └────┬─────┘
   30天没动静 │
        ┌────▼────┐
        │ dormant │  不再注入上下文
        └────┬────┘
   90天没动静 │
        ┌────▼─────┐
        │ archived │  移出主索引
        └──────────┘
```

## 注册的工具

| 工具 | 作用 |
|---|---|
| `memory_write` | 写入一条记忆 |
| `memory_query` | 关键词检索（BM25） |
| `memory_stats` | 统计与预算告警，可触发保留期清理 |
| `memory_promote` | 在层级之间移动 |
| `memory_forget` | 归档（不删除，仍可检索） |

## 安装（已验证）

以本地 bundle 形式装入 DSH profile：

```json
// ~/.dsh/profiles/desktop/package.json
{
  "dependencies": {
    "dsh-cold-hot-memory": "link:E:/DeepSeekHarness/dsh-plugin-memory"
  },
  "dsh": {
    "profile": {
      "bundles": ["@deepseek-ai/dsh-base", "@deepseek-ai/dsh-web-app", "dsh-cold-hot-memory"]
    }
  }
}
```

然后在 profile 目录执行 `pnpm install`，重启 DSH。

**验证方式**：插件启动时会往 `.runtime/loaded.log` 写心跳，正常应看到五行：

```
module-imported → apply-start → imported-dsh-tools → imported-dsh-llm → tools-registered
```

## 写 DSH 插件的三个坑（亲测踩过）

1. **模块顶层不要 `import` 第三方包。** 一旦宿主里解析不到，整个模块在导入阶段就失败，而 DSH 对非必需插件只给一条不可见的警告——界面照常启动，你以为装好了，其实没加载。
   修法：顶层只 `import` 本包文件和 `node:` 内置模块，第三方包放到 `apply()` 里动态 `import()`，失败时写进心跳。

2. **link 安装的包必须自带 `node_modules`。** 宿主的模块解析不会替你补 peer 依赖。

3. **加载失败没有任何提示。** 除非自己写心跳文件，否则无法区分「没加载」和「加载了但坏了」。

## 设计取舍

**为什么做关键词检索，不做向量检索？**
零依赖、可解释、无额外成本，而且规模小的时候关键词足够准。代价是同义词和语义相似处理不了。等规模上来再换。

**为什么用文件，不用数据库？**
可读、可 diff、可备份、可手工修。代价是要自己处理并发写——目前还没做。

**为什么不干脆取消压缩？**
窗口是硬的，做不到"什么都不丢"。能做的是"丢内容、留指针"：一句话就能追回原文。

**为什么结论不直接改？**
因为三个月后真正想问的不是"现在怎么做"，而是"当初为什么没选另一条路"。改了就没有答案了。

## 已知限制

- 数据模型仍是早期的 `hot/warm/cold` 三层，与设计文档中的三类文件模型不一致
- 无并发写保护（多会话同时写同一项目会冲突）
- 没有 UI
- 检索是纯关键词，无语义相似度
- 没有跨会话的自动合并
- 配置目前读默认值（移除了 schemastery 的 `Config` 导出，以便在没有第三方静态依赖的情况下启动）
